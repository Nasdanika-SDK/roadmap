== Revisions

The chapters say what holds now.
This appendix says when it came to hold, newest first.
An entry has a date, what was decided, and the chapters it changed.
Nothing in a chapter changes without an entry here, and an entry is never rewritten: a later decision gets a later entry.

The entries before 2026-11-11 summarize decisions made while the roadmap was a private file of dated sections.
They are here so that the first cut of the book has its history, and only what is public in them is carried over.

|2026-11-20
|Planned, as the accounting floor's first demonstration: statements arrive. A downloaded OFX or QFX file is taken in as entries in the state `imported` with its ledger balance as an assertion, and duplicates are skipped by the institution's identifier. A notification message is an assertion when it carries a balance and a date, and an expectation when it does not, read only from named senders with a valid signature, through a mail folder as a volume. An agent proposes other legs, reads formats no mapping knows, and looks for the slip when a balance does not hold, and a person confirms. A direct connection to banks, through an aggregator or by scraping, is not planned. The accounting floor keeps its place in the order.
|<<model-tower>>

|2026-11-20
|The value of graphs that learn is in the picture, so simulation on drawings comes first: a system or a process drawn in Draw.io, with a calculator on each element that is deterministic, random or trained, and calculators trained alone from load tests, on a component's own time and with the range they were trained on, then composed. The reader is an architect who wires a new solution into an existing architecture. A dense network is a model in Xcore, with layers and weights rather than neurons as objects, weights written raw by a converter of the binary resource, training by code of our own, and a neuron view on a pump for learning. ATMs fit learning along connections and would not draw readers, so they move from the first demonstration to the last steps. The first demonstration is simulated components with a known behavior, whose composition the calculators must predict.
|<<designed-and-waiting>>

|2026-11-20
|Planned, as a demonstration: graphs that learn. A connection has four bindings, a value and its correction each way, and when a correction is a gradient this is back-propagation between nodes. That revises the assessment of 2026-11-10 that bindings could run a graph network and not train it. A node may be of any kind, and offers to predict, to learn locally, to propagate a target, or to propagate a gradient. Corrections accumulate rather than coalesce, and are trained one sample at a time on a pump. The demonstration is a synthetic fleet of ATMs, and its third step, local learning compared with no neighbors, decides whether the rest is built.
|<<designed-and-waiting>>

|2026-11-19
|IAM writes its conditions in CEL, the language made for them. The model keeps how entries combine, and CEL is only the conditions. Every expression of the sketch becomes an evaluator, selectors answer whether an entry covers one target rather than compute a set, `inGroup()`, `hasRole()` and `engaged()` cover what CEL cannot recurse through, an `env` variable carries time, channel and region, and policies are checked when they are loaded. Errors fail closed: an error in an allowing condition does not grant, and one in a denying condition denies. Open: how the engine applies that rule, and whether CEL for Java has the partial evaluation that would turn a policy into a filter at the source.
|<<core-nano-models>>

|2026-11-19
|XPath is not used on model objects. Model objects are selected with CEL and a few functions declared to its checker, `container()`, `contents()`, `allContents()`, `ancestors()`, `root()`, `resource()` and `isA()`, which give what XPath's axes would have, with checking against types. XPath on objects has no standard mapping, its usual library can call Java methods, and it would be a second language for one job. XPath stays for XML documents, such as SVG, on the JDK. The change nano-model selects with CEL alone, and an agent has four surfaces to be offered from, not five.
|<<runtime-models>>, <<target-state>>, <<core-nano-models>>, <<opgraph-and-nsml>>

|2026-11-19
|CEL is the default language of evaluators: in model files, in the selectors and values of the change nano-model, for Meta, for columns of tables and lists, and for bindings. It is checked against an EClass or a Meta class when a model is loaded, and its conditions lower into the expression model. SpEL is for annotations in Java, evaluated against Java objects, such as a selection annotation that resolves a method to an element of a drawing, and never for what comes from a file or an agent. JavaScript runs on GraalJS in a sandbox whose policy depends on who wrote the script, and the script evaluator does not take JavaScript. Each language is a module that contributes an evaluator through a service. The surfaces offered to an agent are chosen by evaluation, with Markdown and CEL by default. Open: whether the core model's `SpelEvaluator` and Draw.io's `$spel` properties are deprecated.
|<<runtime-models>>, <<target-state>>, <<core-nano-models>>, <<drawn-screens>>, <<opgraph-and-nsml>>

|2026-11-14
|All the polymorphic user interface needs is a lineage: a sequence of things to ask for a view, nearest first, which does not have to be a line of specialization. |2026-11-14
|Observed waypoints. A waypoint still does not know its children. A client that needs to follow an execution forward makes the root observed, and every waypoint after it shares the root's publisher of two events: arrived and left. A step means "done here and going there", and `close` means "done here and going nowhere". A subscriber builds the children, moves a ball on a diagram or records how a capability was configured. This answers the open question of whether a waypoint tracks its children.
