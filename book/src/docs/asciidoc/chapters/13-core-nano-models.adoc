[#core-nano-models]
== Core Nano-models

[horizontal]
Capability:: Small aspects that many models share, defined once in the core model: relationships, changes, occupancy in time and other dimensions, kinds, stakeholders and what they are shown, documents, charts, and examples.
Demonstration:: `NanoModelTests` in `models/core`, which instantiates each one.
Status:: [.sketch]#SKETCH# in `models/core`: eight Xcore files that generate and compile against the released core model. Role, IAM, Seal and Lifecycle are in `models/core/sketches` as they are in the tower today.
Depends on:: The runtime's core model.
Value and effort:: High, and each is small. Every model above the core gets them for nothing, and several models in the tower shrink when they arrive.
How to help:: Read the one closest to your work and say which word is wrong. Naming is the hard part of a nano-model and the part that cannot be changed after release.

=== What a nano-model is

A Maven module can hold many Xcore models.
A nano-model is one file: an aspect small enough to read at once, in a package of the core module, with a namespace of its own.
It is in core because nearly every model needs it and because it needs nothing that core does not have.
A model with other dependencies, other users or another pace of change is a module of its own, which the SDK calls a micro-model.

The nano-models depend on each other in a line, so there is an order in which to read them and no cycle to untangle.

[cols="1,2,3",options="header"]
|===
|Nano-model |Builds on |In one line

|related |core |Relationships as model elements
|change |core |Changes as data, with selectors and computed values
|occupancy |related, change |A subject occupies a box in dimensions, of which time is one
|kind |change, occupancy |Classification as data, which can configure
|enterprise |core |Stakeholders, concerns, viewpoints, formats and channels
|document |enterprise |Structure in the model, text in a named format, data in frames
|chart |document |A frame of data and the series drawn from it, as a block of a document
|example |core |An input, the output expected for it, and why
|===

Where a later nano-model needs a class of an earlier one to say more, it specializes that class, and only that class, and only when something needs it.
A role model that needs documents with authors specializes `Section`, and leaves the rest of the document model alone.

==== The pattern

Most nano-models have the same four parts, shown here by the kind model:

`AbstractKind`:: What a list holds: either of the two below.

The reference class was designed before one fact about EMF was put to use here: containment can cross resources.
A contained object may live in another file, so splitting a model over files does not need a reference class.
A reference class stays where the user of a definition has something of its own to say about the use, and it may go from the nano-models where it has not.

=== Related

A reference says that two elements are related.
A relationship says so and can be asked about, because it is a model element: it has an identity, documentation and provenance, and other nano-models give it more.
`Related` is the interface of an element that has such relationships.

The architecture model of the tower is mostly this: elements, containment and relationships that are objects.
With `Related` in core, little of it is left to define.

=== Change

EMF Change describes a change by pointing at the objects it changed and holding the values it set.
The change nano-model keeps the idea and changes two things.
A change finds its objects with a *selector*, an evaluator run in the context of a host.
And a new value can be *computed* from that context.

So a change can be written before the objects it applies to exist, kept in a catalog, and applied to many hosts.
Two nano-models need exactly that: a kind applies its changes to whatever it classifies, and a transition applies its changes to what moves.

A change is a plan.
It can be validated, shown to a person and approved before anything is applied, which is why it is also the command an agent should write with: read with a query, write with a change.
Applying a change is recorded by EMF's change recorder, whose description is the reverse of what was done.

Three rules come with it.
Changes apply in order, and each sees the result of those before it.
A change sets values in the structure its host has and never adds to that structure.
And selectors and values have no side effects, with CEL as the language for catalogs that are not trusted to run scripts, with a few functions for moving through a model, as <<evaluator-cel>> says.

=== Occupancy

The sketch below is a placeholder: a first statement of the idea, to be worked out when something needs it.
It can wait, and the next release does not include it.

Most models treat time as two date columns.
Occupancy treats it as one dimension among others: a jurisdiction, a version line, a level of sensitivity, a floor of a building.

A *region* is a box, with at most one extent per dimension.
An *occupancy* is the recorded fact that a subject is in a region.
Plans, the present and history are then one model read at different coordinates: a person to be hired next year, a control that applies only in one jurisdiction, a price valid for a quarter.

[source,java]
----
include::{nano-test}/NanoModelTests.java[tag=occupancy,indent=0]
----
<1> A draft, from the first of November to the eleventh. The end is exclusive, and the model says so.
<2> Published from the eleventh, with no end: unbounded, not unknown.
<3> A transition from one occupancy to the other, with the change it makes to what moves.

The rules are in the header of `occupancy.xcore`, and four of them prevent most mistakes.
A dimension that a region does not mention is unconstrained.
Whether a bound is inclusive is stored and never assumed.
A shape is a union of boxes, two occupancies and not a polygon.
And an occupancy is a record: a correction is a new occupancy that names the one it replaces.

`Temporal` and `Period`, which the older core model had as special cases, become a coordinate and an extent on the calendar dimension.
Stages of a lifecycle, presence in a place and participation in an engagement are occupancies with one more reference each.

=== Kind

A class says what an element is, for good.
A kind says what it is classified as, and that can be one of several, can come from a catalog that someone else publishes, and can stop applying.

A kind can also configure.
It carries changes, and they apply to what it classifies: the size of a machine, from a vendor's catalog, sets the memory of every machine classified with it.

[source,java]
----
include::{nano-test}/NanoModelTests.java[tag=kind,indent=0]
----
<1> A change that sets a feature, as a constraint: a host that says otherwise is in error.
<2> A use of the kind, by reference, in a classification.
<3> The catalog and its user are saved as two files.
<4> Loading the user finds the kind in the catalog's file.

The boundary is one sentence.
A kind sets values in the structure its host has and never adds to it; a kind that wants a feature its host's class does not have wants to be a class.

Where kinds specialize several others, the order of their changes is the C3 linearization, the one Python uses for classes.
And changes are layers over the host and not edits of it, so that ending a classification removes a layer and nothing has to be undone.
Neither is built yet.

A kind may also choose a view.
The polymorphic user interface asks along a lineage, and the kinds of an element can be part of it, before its class: <<lineage-providers>>.

=== Enterprise

Every effort has stakeholders with concerns, and few write them down.
The enterprise nano-model is the first model an effort should make: who the stakeholders are, what concerns each, what they are shown to address it, in what format, and over what channel.

The vocabulary is that of ISO/IEC/IEEE 42010, with formats and channels added.

[source,java]
----
include::{nano-test}/NanoModelTests.java[tag=enterprise,indent=0]
----
<1> A channel accepts formats.
<2> A stakeholder has formats in order of preference.
<3> A viewpoint's documentation says how to read what is made from it.
<4> A viewpoint names the kinds of things it is made of. A kind of representation element is the class of a representation model, here the table of the document nano-model.
<5> What can be sent to whom is then computed: the formats that the stakeholder takes and the channel accepts.

The model is small because EMF already has most of the full enterprise model's kinds.
A kind of semantic element is a class, a semantic element is any object, and a kind of representation element is a class of a representation model.

It has two uses.
One is documentation: a "monthly statement" viewpoint that explains how to read a statement, a chart that explains itself, which matters most for something new.
The other is a request.
Asked for a viewpoint in a format over a channel, the polymorphic user interface builds the view, and the rendered view can open its viewpoint's documentation as help: a link on a page, kbd:[F1] in a terminal.

A third use is further out.
The same rows can route changes as they happen, each stakeholder at a pace of their own: <<reactive-enterprise>>.

It also explains why the runtime has several formats for one picture.
SVG is for people reading a page or a book, Draw.io for people who edit, and Markdown or the model itself for agents.
Each is a row of a stakeholder, a channel and a format.

The core model's `Documented` has sections and content.
The document nano-model replaces them, and it starts from the enterprise nano-model: a document is a view, and a section is a representation.
It is planned for the next release, whose focus is documentation: <<document-model-release>>.

==== Data

Data is a *frame*: named columns of equal length, as a data frame of pandas is.
A value is text, read by the type of its column, and an empty value is missing.

[source,java]
----
include::{nano-test}/NanoModelTests.java[tag=frame,indent=0]
----
<1> A frame is a model element, so its documentation can say where the numbers came from.
<2> A label is what a reader is shown. The name is the key that a series of a chart uses.

A table can be made from a frame, and a chart of <<chart-nano-model>> always is.
A frame is the data, and a table or a chart is a representation of it, so "a chart replaced a table" changes the representation and not the data.
A table is also what an agent and a Markdown page should get: the numbers, and not a picture of them.

A table or a chart holds an `AbstractFrame`, which is the pattern of the kind model: the `Frame` itself, or a `FrameReference` to a frame held elsewhere.
Two needs are kept apart here, and each has its own answer.

* A frame in a file of its own needs no reference. The containments of frames resolve proxies, so a contained frame can be saved in a resource of its own, such as the results that an evaluation run wrote, and stay where it is in the document.
* A frame shown more than once needs a reference, and someone to hold it. The document holds it, in its frames.

[#chart-nano-model]
=== Chart

Some results read better as a chart than as a table: an evaluation across versions, a cost against a score, a share of outcomes.
The chart nano-model makes a chart a block of a document, so a chart goes wherever text and tables go, and the writers of documents write it.
It specializes `Block` of the document nano-model and leaves the rest of that model alone.
Its data is a frame of the document model: <<document-frames>>.
It goes into the next release with the document model, since evaluations are part of documentation.

The classes are those of Recharts, a charting library for React, and so are the defaults, where Recharts has one.
Someone who knows Recharts can read a chart in the model, and an HTML writer is close to a copy.

==== Where it departs from Recharts

* What Recharts has for the browser is left out: tab indexes, ARIA flags, CSS classes, event handlers, and positions it computes. A chart is also written to places that have none of them. A writer that needs more reads it from the attributes of the chart, which a chart has as a block, under a prefix of its own such as `echarts.`.
* The x axis has the categories and the y axes have the values, in either layout. A vertical layout turns the chart for horizontal bars, where Recharts asks for the types of the two axes to be swapped as well.
* A cell names the category it styles. A cell of Recharts is matched by position, which breaks when the rows are sorted.
* A scatter holds its z axis, where Recharts has it on the chart and a scatter names it by id. Its range is 64 to 1024 square pixels, where Recharts has 64 to 64, which leaves every point one size. A shade and a border from columns are not in Recharts, which sets them with a cell per point.
* A line is 2 pixels wide, as in ECharts. Recharts has 1, which is thin on a printed page.

==== Surfaces

The model has no dependencies beyond the document nano-model.
Writers have dependencies, and they are modules of their own.
The runtime already has most of what they need.

|Surface |Writer |Needs

|Draw.io

Basic charts need no charting library.
The layout of a bar, line, area, scatter or pie chart is a small amount of arithmetic, and it is shared by SVG and Draw.io.
It is also what is worth testing, since it can be checked without drawing anything.

XChart is a fair choice where a picture is all that a format takes.
Version 4.0.4 is under the Apache 2.0 license, needs Java 11, and has no required dependencies: writing SVG and PDF takes optional ones.
It draws with Java2D, so it needs the `java.desktop` module, and neither its POM nor its README mentions a module name.
It is not the way to SVG here: what it writes is what Java2D drew, with nothing that says which shape is which bar, and it cannot write Draw.io.
The model is the API, and a library is one writer behind it.

The layout is three small pieces, and none of them knows SVG.
`Ticks` puts the ends of a numeric axis and its ticks at round numbers, steps of 1, 2 or 5 times a power of ten, which is Heckbert's method.
A band per category places bars and points, and Recharts' gap between categories and gap between bars divide it.
Geometry is worked out along the categories and along the values and turned into x and y last, so a vertical layout is a swap and not a second drawing.
The Draw.io writer is to take these pieces as they are, and they move to a module of their own when it does.

The writer applies one set of rules to every chart, and a chart can still say otherwise where the model lets it, such as the color of a series:

* Eight categorical colors, in an order checked for color vision deficiency, used in order and never by rank.
* Lines 2 pixels wide. Bars at most 24 pixels thick, square at the base and rounded at the end.
* Dots of at least 8 pixels, ringed in the color of the surface so they stay legible where they cross a line. A gap of 2 pixels in the same color between stacked bars and between slices.
* A grid of hairlines, and text in ink and never in the color of a series.
* The title is the accessible name and is not drawn, since a document writer makes it a caption.

=== Role, IAM, Seal and Lifecycle

Four models of the tower are to become nano-models: who is responsible, who may see and do what, what is signed and encrypted, and what stage something is in.
They are the lowest floors of the tower, and everything above them inherits what they say.

Their Xcore is in `models/core/sketches`, as it is in the tower today, on the older core model.
Moving them is a rewrite and not a rename:

* *Role.* An assignment of a role is an occupancy, and a role in a catalog is a kind. Sections with authors and editors specialize the section of the document nano-model.
* *IAM.* A grant valid in one region during one period is an occupancy. Levels of sensitivity are a dimension, so "cleared up to confidential" is an extent.
* *Seal.* Signatures are made over content digests, which are planned for core.
* *Lifecycle.* A stay in a stage is an occupancy, and a transition between stages is the transition of the occupancy nano-model, with its changes.

Each should be smaller afterwards than it is now, which is the test that the nano-models below it are right.

[#iam-conditions]
==== Conditions in IAM

CEL was made for the conditions of access policies, and IAM is where it fits best.
Google Cloud's IAM conditions are CEL over the request and the resource, and Kubernetes writes its admission policies in it.
The sketch is shaped for it already: the example of a subject selector, `principal.department == "Risk"`, is CEL as it stands, and the conditions of entries and permissions are over the subject, the element and the environment.

The model keeps the structure of a policy, and CEL is only its conditions.
How entries combine is said by the model: nearest first, an explicit deny over an allow, and no match as a deny.
So a policy stays a model that can be documented, compared and reviewed.
A policy language such as Cedar or Rego would carry both, and the model would be lost.

Five things change in the sketch.

* *Every expression is an evaluator.* The string of a subject selector becomes an evaluator, as the conditions are, with CEL as the default of <<evaluator-cel>>.
* *Selectors answer for one target.* A check of access is about one subject, one action and one element. So the selectors of targets, resources, subjects and actions say whether an entry covers a given one, as in `target.isA("Account") && target.ancestors().exists(a, a == element)`, rather than compute a set. A test is cheaper than a set, and it can be pushed down.
* *Functions for what CEL cannot recurse through.* `inGroup()` for membership through nested groups, `hasRole()` through hierarchies of roles, and `engaged()` for a subject engaged with an element in a role of the role model. Each declares its cost, since a walk through groups is not free.
* *The environment is declared.* An `env` variable carries the time, the channel and the region, for access limited to a period or a stage. Access in one region during one period is an occupancy, as above.
* *Policies are checked when they are loaded.* A condition that names an attribute a subject does not have is rejected when it is saved, and does not quietly allow or deny when it runs. That is what lets an assistant draft a policy: the checker judges its structure, and a person approves what it means, as a change is approved.

Errors fail closed.
In CEL, `error || true` is true, and an error on its own is a value that a policy has to interpret.
An error in an allowing condition does not grant, and an error in a denying condition denies.
If an error meant "does not apply", a denying entry would fail open.
How the engine applies the rule, and the tests that show it, are open.

Partial evaluation is open too.
A condition evaluated with the subject known and the resource unknown leaves a condition on resources.
Lowered into the expression model, it answers "which documents may this person see" as a filter at the source, and not as a check of every row after the fetch.
The Go implementation of CEL does this. Whether the Java one does as well is to be checked.

=== What is not there yet

* [.planned]#PLANNED# *Applying changes:* the engine that evaluates selectors and values, applies changes in order, and reports a change that does not fit its host.
* [.planned]#PLANNED# *Region arithmetic:* whether one box contains or meets another, and which occupancies are current at a coordinate.
* [.planned]#PLANNED# *A model at a coordinate:* the projection of a model to what holds at one place and time, so that a model can be released for a jurisdiction and a date. <<target-business>> has the use.
* [.planned]#PLANNED# *Catalogs as resources:* formats, channels and a few stakeholders that models can refer to, as the first content.
* [.planned]#PLANNED# *Chart writers:* Draw.io, the terminal, HTML and Markdown, as listed in <<chart-nano-model>>. SVG is a sketch: <<chart-svg>>.
* [.planned]#PLANNED# *More encodings:* a shade that diverges from a neutral middle, for a value with a sign, and the encodings of a scatter in the writers other than SVG. Size, shade and border by column are a sketch: <<chart-cost-benefit>>.
* [.planned]#PLANNED# *More charts:* a percentage stack, sparklines, and the Sankey chart that the enterprise model already gives as an example. Points that say which model element each one shows, where today only a series can.
* [.planned]#PLANNED# *Facets:* an element that has an aspect for a while, where today it would have to inherit it for good.
* [.planned]#PLANNED# *Generated references* for these models, in this book, once the runtime generates them.
