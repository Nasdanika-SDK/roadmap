[#widgets]
== Widgets

[horizontal]
Capability:: A view written once, against kinds such as text, link, section, list and table, and rendered into any format that provides them: Markdown, a terminal, and later AsciiDoc, HTML with Bootstrap and a diagram.
Demonstration:: `RoadmapViewTests` in `tests/widgets`: one view of this roadmap's runtime items, rendered four ways. Its output is in this chapter.
Status:: [.sketch]#SKETCH# in `runtime/widget`. Markdown, GitHub Flavored Markdown and a neutral terminal context are in the module. AsciiDoc, HTML and interaction are [.planned]#PLANNED#.
Depends on:: The runtime's `common` for the capability framework, and <<bindings>> for values that change.
Value and effort:: High for medium. The polymorphic user interface has a vocabulary in the model and nothing at the level of Java. This is the missing half.
How to help:: Write a context for a format you need. AsciiDoc is the next one, and its design is below.

=== Why

The runtime chooses a view by the class of what it shows.
The SDK book's example of that returns an HTML node from every view, so every view is an HTML view, and a second format means a second set of views.

A view written against kinds does not name a format.
It asks for a table and says what the columns and the rows are, and the format decides what a table is.
The choice then has two halves, the class of the element and the format asked for, and this module is the second half.

The split is the one the `volume` module makes.
Developers write against an API, and a format implements an SPI, as `PathVolume` implements `Volume`.
Widget toolkits have always been built this way, and the ones that failed did so by offering only what every platform had.
So from the first version there are two ways out: a kind that a format does not have is simply absent, and a format that can do better than the neutral kind provides its own.

=== A widget

.A widget renders itself into a context
[source,java]
----
include::{widget-main}/Widget.java[tag=widget,indent=0]
----

The context's type is the format: `MarkdownContext`, `TerminalContext`.
What rendering gives back depends on the format too: nothing for Markdown, which is written and not built, and the number of rows used for a terminal.

A widget is asked for by the *type* of the context and given the *instance* only when it renders.
The reasons are practical.
A terminal draws many times a second, each time into a new area, so a widget bound to an instance would hold a stale one.
Nested widgets render into derived contexts, a sub-area or a deeper heading level, and one child may render into many of them.
And a widget built before any context exists is a value: it can be passed around and rendered into two terminals, or into a file and into an answer to an agent.

`TerminalContext` abstracts only what the neutral kinds need: an area, text at a position, and a style in logical terms.
Colors are logical too, named for what they mean: primary, success, danger.
The names are Bootstrap's, so a view says "danger" once, and a page, a terminal's palette and a diagram each show it their own way.

A terminal widget gives back the rows it used, which is how widgets are stacked without a pass to measure them first:

[source,java]
----
include::{widget-main}/terminal/TerminalKinds.java[tag=section,indent=0]
----
<1> The title, in a context where text is bold and in the primary color unless it says otherwise.
<2> Each widget of the body gets what is left of the area, indented.
<3> And says how many rows it used.

A widget cannot draw outside the area it was given, and a table reads only the rows that fit.
A table of a million rows on a screen of five reads three of them.

`GridContext` implements the terminal context over a grid of characters in memory.
It is the smallest provider, and a useful one: a test asserts on it, a log can include it, and an agent can read a screen as text.

=== A binding is a value

Every value a kind takes is a supplier, so a binding from <<bindings>> is a value.

[source,java]
----
include::{widget-test}/WidgetTests.java[tag=binding,indent=0]
----
<1> The date is a binding. The view does not know.
<2> The same widget, rendered again, reads the value as it is now.

A static format reads the value when it renders, and a screen reads it on every frame.
The widget is the same.

State that outlives one rendering, a scroll position or a selection, is not the widget's.
The screen owns it and passes it in, as TamboUI and Ratatui do, or the widget reads it through a binding.
Otherwise binding late to a context would only move the early binding into the widget's own fields.

=== What is not there yet

* [.planned]#PLANNED# *An AsciiDoc context.* AsciiDoc is a format of several files. Widgets ask for sections, and the context decides through a policy which sections become files of their own: by level, as a book splits into chapters, or by class, as a reference has a file per class. A locator maps a model element to a path and an anchor, so a link to an element is written before the element is rendered. `Include` is a kind that only AsciiDoc has.
* [.planned]#PLANNED# *The first consumers:* the glossary of a Meta package, rendered as Markdown and AsciiDoc with the bank model as the example, and the documentation of a command line, rendered from its saved command tree (<<runtime-models>>).
* [.planned]#PLANNED# *An HTML context with Bootstrap,* beside the HTML models it depends on, and a context that builds the document model of <<core-nano-models>>.
* [.planned]#PLANNED# *Interaction:* `Action`, `Selection` and `Input` as kinds that static formats do not provide, and `Tree` and a form, each arriving with the first screen that needs it.
* [.planned]#PLANNED# *A table that scrolls,* with its position in a state object.

=== Why not something that exists

The question will be asked, and the survey was made.
Nothing found covers documents and screens with one vocabulary in Java.

* *Maven Doxia* has a sink with calls for document elements, and writers for several formats. It is for documents only, and its list of calls is a good checklist for the kinds.
* *json-render and Adaptive Cards* are catalogs of components rendered by several hosts. They are the closest in idea and are not Java libraries. Each could be a context here.
* *JSON Forms and EMF Forms* render forms from a model and write no documents.
* *Pandoc* converts between document formats through one model, which is the plan for conversions here, and has no screens.

The answer to "why not" is then the same each time: this is a small API over what a format already has, and where a format has a library, the library is its provider.
