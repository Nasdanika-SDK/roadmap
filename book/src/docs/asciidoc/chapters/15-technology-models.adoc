== Technology Models

A technology model describes what a system or a format holds, in the system's own terms: the issues of a tracker, the commits of a repository, the cells of a workbook.
It is for reading and writing, and it is tested by round trips.
It makes no claim about what the content means.
Meaning is given by cross-referencing it with the models of <<model-tower>>: a person in a Git history is a person in the organization, and a module in a build is an asset in a threat model.

The older Nasdanika has such models, most of them defined in Ecore, each in a repository at {models-org} with a loader and a generated site.
The ones below are to be migrated.
The others stay where they are for now.

=== What migration means

A model does not move as it is.
Following the rule of <<direction>>, salvage and do not port, it comes as a small model and its integrations come as adapters.

* *The model* is rewritten in Xcore on the runtime's core, generated by Maven with no IDE, with its namespace under the SDK's.
* *The loader goes through a volume.* A system is presented as a volume of models, with relative references, so that a snapshot is a copy, and repeated scans go on until nothing changes.
* *The client is the JDK's.* Where the older loader used a vendor's library, the new one calls the REST API with the JDK's HTTP client, so a model of one system does not bring a second HTTP stack.
* *It gets a book,* with listings from its tests.

A snapshot is the reason to load a system into a model at all.
Data loaded from a system is saved and worked on later: enriched in several passes without asking the source again, examined after a temporary token has expired or where the source cannot be reached, and compared with the snapshot of the next quarter.
Trackers limit how fast they may be read, and scanning thousands of repositories on every run is slow, so a snapshot is also the practical answer to cost.

Once a system is a volume, <<commander>> is a way to walk through it, and a file in a repository on a server can be edited where it is.

=== The models

[cols="1,3,3",options="header"]
|===
|Model |What it holds, and its state before the SDK |What the SDK version changes, and what it waits for

|Coverage
|Java code coverage, loaded from JaCoCo's execution data and class files. Used alone or with the Java model: which methods no test reaches.
|Joined with the Java model through references. Waits for the Java model.

|Excel
|Workbooks, sheets, rows and cells, with a loader and a resource factory, so a workbook is a model resource.
|Read through a model generated from the format's schema, with a library only as an optional adapter for formulas and old binary files. Workbooks of the size of a model are the use: configuration, mappings, glossaries, catalogs. Waits for the schema-model route.

|Git
|The object model of a repository: blobs, trees, commits, references, branches and tags.
|A Git volume on JGit, which the runtime's bill of materials has. The core model's Git marker, which records where an element came from, is its first user.

|GitHub
|Organizations, repositories, people and what they do there. The one with an Xcore sketch, `models/technology/github.xcore`.
|A system volume over the REST API, and files committed through it without a clone.

|GitLab
|Users, groups, projects, repositories, branches and commits, loaded for cross-referencing with an organization: who owns what, which branches are stale.
|As GitHub, over the REST API with the JDK's client in place of a client library. The two share the Git model.

|Java
|Modules, packages, classes, fields and methods, and compilation units, loaded from sources and from the reflection API.
|The runtime has a JVM model, of a running program. The Java model is of sources: for analysis, for generation, and with coverage for finding what to test.

|Jira
|Users, projects, issues of several types and the relations between them, categories, releases, filters and boards.
|A system volume with snapshots. Comparing the state of a hierarchy of projects once a quarter is its plainest use.

|SQL
|Two models: the metadata of a database as JDBC reports it, with generators of models from it and loading of data into them; and the syntax tree of SQL statements.
|Metadata first, as a system volume. The syntax tree follows the pattern of the Cypher model.

|Python
|A model for generating Python sources.
|Perhaps not migrated. Nothing on this roadmap generates Python.
|===

None of these has a date.
Each moves when something needs it, and the order of the table is alphabetical, not a ranking.
The candidates to go first are Git, since provenance already refers to it, and whichever of GitHub and GitLab a first reader asks for.

=== Formats already in the runtime

For completeness: the runtime {runtime-version} has models of Draw.io diagrams, of diagrams in general with layout by ELK, of SVG, of presentations, of HTML with Bootstrap, and of TypeScript and React.
They are [.available]#AVAILABLE# and described in their own books.
Visio, PowerPoint and Word wait, with Excel, for models generated from the formats' schemas.
