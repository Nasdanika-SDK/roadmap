[#explorer]
== Nasdanika Explorer

[horizontal]
Capability:: A tree on the left and, on the right, a view of what is selected in it: a way to walk through a structure one element at a time and see, and later edit, what is known about each. Over the modules of a JVM today. Over the elements of a model and the pages and shapes of a diagram next.
Demonstration:: `ExplorerTests`, `ModuleViewsTests` and `TerminalLoopTests` in `runtime/explorer`. After the build, `java -jar` runs it.
Status:: [.sketch]#SKETCH# in `runtime/explorer`: a prototype that navigates and views. Editing, and exploring a model or a diagram, are [.planned]#PLANNED#.
Depends on:: <<widgets>> for the views, <<terminal>>, the runtime's `volume` module for the tree, and TamboUI {tamboui-version} for the tree widget.
Value and effort:: High for small. It is the navigator with details that <<commander>> and <<model-tower>> ask for, and the authoring half of the diagram documentation in <<target-state>>.
How to help:: Make a generic volume of something you know, with a view for its content, and say what the explorer did not let you do.

=== Why

I have many diagrams, and many of them are a pixel deep: boxes and lines with nothing behind them.
Drawing a diagram is spatial thinking.
Documenting it is sequential thinking: go through its elements one by one, and for each write down what is known, or read what is already written and correct it.
A canvas is the wrong tool for the second kind of work.
It shows everything at once and one element's documentation in a small dialog.

The explorer is the tool for the sequential half.
It shows the structure as a tree and gives the rest of the screen to the element that is selected.

It differs from the commander in what it is about.
The commander has two places and is about moving things between them.
The explorer has one structure and is about what each thing in it is.
They share what they stand on: both show a volume, and both are an application without a terminal, driven by a test.

=== Running it

[source,text,subs="attributes"]
----
mvn -q package
java -jar runtime/explorer/target/explorer-{revnumber}.jar
----

It opens on the modules of the JVM that runs it, which every reader has.
Started this way those are the modules of the JDK.
`explorer` and `explorer.cmd` beside the module's `pom.xml` run the same line.

=== From the command line

The explorer is meant to be a command, after a command that supplies what to explore:

[source,text]
----
nsdk model architecture.drawio explore --edit
----

`model` loads `architecture.drawio` as a model. The runtime has the model of a Draw.io file: a document, its pages, their layers, nodes and connections.
`explore` opens the explorer on it, the tree of the diagram's elements on the left.
With `--edit` the right pane is an editor where one exists for the selected element, and a view where none does.
Without it kbd:[F4] opens the editor, as it does in the commander.
Which of the two is the default is a setting.

A person then walks the tree of the diagram, reads what is written about each element and writes what is missing.
What is edited there is the documentation stub of the element, described in <<next-transition>>, and not the diagram file.

The line is a design.
The released runtime has the wiring that lets `explore` receive what `model` supplied, and neither command exists yet.

=== What is not there yet

* [.planned]#PLANNED# *A volume of model elements.* Containment as folders, attributes as content, and references as links, which the volume interface already has a capability for. With it the explorer opens any model the runtime loads.
* [.planned]#PLANNED# *Views by class.* The view function as the polymorphic user interface: a view per class from the module that knows the class, and a reflective view for what nobody claimed. The views of Meta's classes come first, since they document every metamodel.
* [.planned]#PLANNED# *Editing.* kbd:[F4] on an element opens the editor of the commander on the element's documentation, or on an attribute. Saving goes through a command, recorded and validated, as <<bindings>> describes for input.
* [.planned]#PLANNED# *Commands by type.* What can be done with the selected element depends on its class, and the key bar shows it. This is the commander's "any tree, with commands by type", in the screen that fits it better.
* [.planned]#PLANNED# *Search and filter* in the tree, and going to an element by its path or id.
* [.planned]#PLANNED# *Links in a view.* A view that mentions another element lets the reader go to it, and come back.
* [.planned]#PLANNED# *The `explore` command,* and a base terminal command under it and the commander, as <<terminal>> describes.
* [.planned]#PLANNED# *A tree kind* in the widget module, extracted from this prototype.

The explorer was run from its jar with a key piped to it, and through JLine's in-memory terminal in `TerminalLoopTests`.
